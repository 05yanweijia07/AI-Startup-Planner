# Reference Routing Rules

## Goal

Select the smallest set of professional References that can complete the user's actual task safely and well. Routing is based on required work, project context, and dependencies, not on every industry label attached to the venture.

## Five-step routing

1. **Classify the request.** Identify primary and secondary task types, requested deliverable, relevant gate, and constraints.
2. **Match triggers.** Search the module registry's trigger conditions and exclusions. Treat `planned` modules as unavailable content, not as loaded expertise.
3. **Resolve dependencies.** Add only prerequisites necessary to perform this task. Reuse accessible project records rather than reloading unrelated context.
4. **Set priority.** Mark each candidate `MANDATORY`, `RECOMMENDED`, `OPTIONAL`, or `EXCLUDED`; explain an exclusion only if it may surprise the user or changes the result.
5. **Build an execution plan.** Load required content in dependency order, then integrate results against one task objective. Present the plan only when complexity makes it useful.

## Industry routing

Use primary, secondary, and supporting industry tags as context. Route by the business activity involved. A food and cultural-gift venture may require food operations for a packaging task and creative IP for a brand-story task; it does not require loading both domains for every request.

For cross-domain work, define a shared outcome and identify interfaces between modules. Safety, legal, or regulatory checks that apply to the actual activity cannot be excluded merely because another module is primary.

## Priority meanings

| Priority | Rule |
|---|---|
| `MANDATORY` | Required to answer the request adequately or meet an applicable safety/quality constraint. |
| `RECOMMENDED` | Likely to materially improve the answer, but not essential to the requested scope. |
| `OPTIONAL` | Useful only if the user wants additional depth or a corresponding deliverable. |
| `EXCLUDED` | Irrelevant, contradicted by scope, or not applicable; do not load. |

## Execution order and integration

- Execute prerequisites before dependent analysis.
- Independent analyses may run in parallel only if the platform supports it; otherwise use sequential execution.
- Keep one authoritative value for each project fact and cite its record/source.
- Integrate module outputs; do not paste incompatible recommendations together without resolving the conflict.
- Identify missing inputs, unavailable References, stale results, and assumptions that materially affect the answer.

## Example routes

| User request | Mandatory | Recommended or optional | Excluded unless new scope appears |
|---|---|---|---|
| Rewrite a brand slogan | Brand/strategy writing Reference when available | Customer positioning context | Financial model, supplier operations |
| Estimate a gift-box break-even point | Costs, unit economics, break-even, required inputs | Packaging/channel costs when relevant | Brand IP design |
| Research a market | Market sizing, segments, customer/competitor evidence, evidence management | Industry context | Financial forecast unless requested |
| Generate a complete business plan | Current state and evidence, relevant market/strategy/financial/operations outputs, plan structure and consistency review | Audience-specific layout or visuals | Unsupported claims and irrelevant modules |
